========================================================================
Tool Runtime 完整工作流：注册 -> 发现 -> 执行
（依据 2-2.pdf《Tool Runtime 设计：让 Tool Call 进入受控执行》整理）
========================================================================

【总览】三个阶段各自只回答一个问题，互不越界：
  注册：平台是否认识这个工具
  发现：当前场景是否应该把它交给模型
  执行：当前这一次调用是否真的允许发生

------------------------------------------------------------------------
阶段一：注册（Registration）
------------------------------------------------------------------------
目的：让 Registry 认识这个工具，与"本轮开不开放"、"现在能不能执行"无关

ToolDefinition 三组字段（工程师注册时要准备齐全）：
  1. 调用契约：name、version、description、input_model、output_model、error_codes
     -> 这是唯一会投影给模型看的部分
  2. 运行治理：permission、risk、timeout_s、retry 策略、dependencies、execution_mode 等
     -> 模型永远看不到，只有 Runtime 使用
  3. 真实实现：handler（真正干活的业务函数）

注册时检查项：
  1. 查重：(name, version) 组合键是否已存在，重复则拒绝
  2. 基础配置合理性：timeout_s > 0，retry.max_attempts >= 1
  3. （生产环境）名称格式是否规范、Schema 能否正常生成、错误码是否重复
  4. 静态依赖检查（加载检查）：API 密钥是否存在、数据目录是否存在等配置层面检查

元数据设计原则：每个元数据字段必须有明确消费者，没有任何代码会读的字段不该加

产出：Registry 里新增一条 (name, version) -> ToolDefinition 记录
边界：注册成功 只代表平台认识它，不代表本轮开放，也不代表已执行

------------------------------------------------------------------------
阶段二：发现（Discovery）
------------------------------------------------------------------------
目的：决定"这一轮该把哪些工具交给模型"
发生时机：模型请求之前，由 Harness 完成，模型完全不参与这个筛选过程

动作：
  1. 根据当前运行模式/场景（如 TOOL_PROFILES[run_mode]）查出本轮该用哪些
     工具、用哪个版本（routes，同时锁定工具名和版本 = 版本灰度路由）
  2. 结合"活的" enabled_state，过滤掉当前已停用的工具（第一层启停检查，
     目的是效率优化：减少模型看到明显不能用的工具、减少无效轮次）
  3. 把结果冻结成 ToolSnapshot
     - @dataclass(frozen=True)，且内部字典建议用 MappingProxyType 包一层，
       连字典内容也不可变（单纯 frozen=True 挡不住内容篡改）
     - Snapshot != 缓存：它的职责是"建好之后不更新"，Registry 之后再怎么
       变（版本切换、新注册），这份快照原封不动

设计原则（4.2）：模型请求和 Runtime.invoke() 必须使用同一个 snapshot 对象，
  显式作为参数传递，禁止 Runtime 内部重新查询 Registry
  -> 防止"协议漂移"：模型按旧版本 Schema 生成的参数，被新版本 handler 处理，
     导致字段名对不上（轻则报错，重则静默曲解数据）

产出：
  1. ToolSnapshot（模型和 Runtime 本轮共用的冻结视图）
  2. Tool Schema（snapshot.provider_tools() 投影出来的结果，只含 name/
     description/parameters，不含 handler、权限、密钥等治理字段）-> 发给模型

边界：模型只能在这份已经筛好的候选集合里做选择，无权决定候选集合本身

---- 模型基于 Tool Schema + 对话上下文，生成 Tool Call（id/name/arguments）----
---- 这是整条链路里唯一需要"推理判断"的环节，前后其他步骤都是确定性逻辑 ----

------------------------------------------------------------------------
阶段三：执行（Runtime.invoke，拆成 prepare -> execute -> finalize）
------------------------------------------------------------------------
目的：确认这一次具体调用是否真的允许发生，并安全地完成它

【prepare 阶段】—— 原则：不该执行的调用，绝不能进入 execute
  1. 查找工具：从 Snapshot（不是 Registry）里查 call.name
     找不到 -> TOOL_NOT_FOUND
  2. 参数校验：用工具的 Input Schema 校验 arguments
     不合法 -> INVALID_ARGUMENT
  3. 权限检查：只从认证后的 ExecutionContext 读 user_id/tenant_id/权限，
     绝不相信模型在 arguments 里自己填的任何字段
     权限不够 -> PERMISSION_DENIED
  4. 风险/审批检查：risk 等级要求审批时，查 call.id 是否在
     ctx.approved_call_ids 里（同样只信可信上下文，不信模型自称的 approved）
     未批准 -> APPROVAL_REQUIRED
  5. 启停复查（第二层检查）：重新查询"活的" enabled_state（不是快照建立
     时的状态，这一步才是真正兜底安全性的检查）
     已停用 -> TOOL_DISABLED
  6. 动态依赖检查（调用检查）：查这个工具依赖的外部系统现在是否健康
     不健康 -> DEPENDENCY_UNAVAILABLE
  7. before Hook：业务方可挂载自定义检查（如工作时间限制），可返回错误
     阻止执行，Runtime 核心代码不需要为这类规则改自己的代码

【execute 阶段】—— 真正调用 handler，处理超时与重试
  1. 调用 handler(**验证后的参数)，真实业务动作在此刻发生，副作用不可逆
  2. 套超时保护，超时 -> TIMEOUT
  3. 重试策略：
     - 幂等操作（只读/可安全重复）：超时或失败后可重试
     - 非幂等操作（写操作：创建/支付/删除）：超时只代表调用方没收到结果，
       不代表下游没成功，盲目重试可能重复创建/重复扣款/重复删除，
       所以最多尝试 1 次，不自动重试
  4. handler 内部真实异常，捕获并归一化 -> INTERNAL_ERROR，绝不泄露原始
     Python 堆栈给外部

【finalize 阶段】—— 保证吐出去的结果干净、可信、可关联
  1. 输出校验：用 Output Schema 校验 handler 返回值
  2. 脱敏：根据 BusinessMetadata 里的 data_classification 等字段处理敏感数据
  3. after Hook：业务方可挂载结果加工逻辑（脱敏、改写），但无法撤销已经
     发生的写操作，因为 execute 阶段的副作用已经真实产生
  4. 审计记录：记 tool_call_id、tool 名、version、tenant_id、user_id、
     outcome(成功或错误码)、argument_fields（只记字段名，不记实际值，
     避免敏感数据进入日志）
  5. 打包成 ToolResultMessage，带着原始 tool_call_id；成功带结果，失败
     只带稳定错误码 + 通用描述（内部地址/密钥名/堆栈信息只留在受控日志，
     不进这条消息）
  6. 写回 Agent Loop 的对话历史（不是直接发给模型），下一轮模型请求时
     才会作为普通文本被模型读到

------------------------------------------------------------------------
批量执行策略（invoke_many）
------------------------------------------------------------------------
判断依据：遍历这批调用涉及的每个工具，检查它在 ToolDefinition 里声明的
  execution_mode 字段（"parallel" 还是 "sequential"）
规则：只要批次里有任意一个工具要求 sequential，整批就退化为顺序执行
  （for 循环 + await 逐条跑）；全部都是 parallel 才用 asyncio.gather 并发
关键点：这个决定由"工具定义 + Runtime 策略"共同做出，模型不参与、也不
  知道这件事存在

------------------------------------------------------------------------
三个核心对象的职责边界
------------------------------------------------------------------------
Registry  : 保存工具定义和版本（"有哪些"），不决定本轮开放，不执行
Snapshot  : 冻结本轮可见工具及其版本（"这一轮能给模型看什么"），建好后
            不随 Registry 变化而变化
Runtime   : 在执行前重新确认状态、权限和依赖（"这一次真的能不能跑"），
            只信传入的 snapshot 参数，不重新查询 Registry

------------------------------------------------------------------------
错误码汇总
------------------------------------------------------------------------
TOOL_NOT_FOUND          快照里找不到这个工具
INVALID_ARGUMENT        参数不符合 Input Schema
PERMISSION_DENIED       调用者权限不够
APPROVAL_REQUIRED       风险等级要求审批但未批准
TOOL_DISABLED           工具当前被临时停用（执行前复查发现）
DEPENDENCY_UNAVAILABLE  工具依赖的外部系统当前不健康
TIMEOUT                 执行超时
INTERNAL_ERROR          handler 内部异常，已归一化，不泄露堆栈
INVALID_OUTPUT          handler 返回结果不符合 Output Schema

------------------------------------------------------------------------
贯穿全文的核心设计原则
------------------------------------------------------------------------
1. 三阶段各自只回答一个问题，互不越界
2. 模型只提议，不决策治理：治理字段从"投影"那一步就被过滤掉，模型看不到
3. 检查必须在副作用发生之前完成：prepare 全部通过才能进 execute
4. 只信可信上下文，不信模型参数：user_id/权限/审批状态必须来自
   ExecutionContext，不能来自模型自己生成的 arguments
5. 快照冻结、不随时间更新：防止模型和 Runtime 用的定义不一致（协议漂移）
6. 分层校验：启停/依赖既在建快照时查一次（效率优化），也在执行前再查
   一次（安全兜底），两次目的不同
7. 错误对模型稳定、对内部详细：模型只看到统一错误码，敏感内部信息只进
   受控日志
8. tool_call_id 贯穿全程：用于关联请求与结果，并发/批量场景下保证正确配对
